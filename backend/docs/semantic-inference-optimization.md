# 语义图谱 CPU 推理优化实验

本轮优化由用户授权；原微调训练、模型权重、语料与评分规则保持冻结。部署默认仍为 `baseline`。各配置是显式实验选项，不是失败回退路径。

**结论：prefix8明显加快缓存后的推理，但未通过完整测试的启用门槛，不推荐作为默认。** 本轮保留全部结果，并在隔离服务器进行临时性能验证；验证后由管理员恢复baseline。恢复是实验结束后的显式配置操作，运行时没有自动回退。

## 预先确定的比较方法

使用同一微调 Q4_K_M 权重（SHA256 `cadbc0a850ad31c712b4441a39775a8969ecdf9c0a762730c2a9a1c4344efd09`）、llama.cpp b11146、完整 48 类 schema、temperature=0、seed=2026、1536 输出 tokens、300 秒模型请求超时。开发集固定使用 need_budget、contact_not_employee、negated_need 三类；测试集使用原来的全部 12 条。不得修改标签、补写模型输出或缩短 schema。

依次比较 baseline、context8、flash8、kv8、prefix16、combined8。配置见 `apps/knowledge_graph/inference_profiles.py`。每组独立启动单槽位服务；第一个样本为冷请求，立即重复一次测热缓存；后续不同样本测跨输入复用。重复样本不计入质量汇总。冷请求指无先前请求的 KV 缓存，不包含启动/加载时间，也不保证操作系统文件缓存是冷的。

| 配置 | 上下文 | KV 类型 | Flash Attention | 前缀复用与消息排列 |
|---|---:|---|---|---|
| baseline | 16384 | F16 | auto | 关闭，原排列 |
| context8 | 8192 | F16 | auto | 关闭，原排列 |
| flash8 | 8192 | F16 | on | 关闭，原排列 |
| kv8 | 8192 | Q8_0 | on | 关闭，原排列 |
| prefix16 | 16384 | F16 | auto | 开启，schema在前 |
| combined8 | 8192 | Q8_0 | on | 开启，schema在前 |
| prefix8（补充组） | 8192 | F16 | auto | 开启，schema在前 |

筛选规则在基线首条及其重复完成后、其他配置结果未知时记录：候选在三个非重复开发样本上的 valid、facts_exact、TP 不低于基线，FP、FN 不高于基线，且无运行失败。合格候选按非重复请求平均耗时选择最快者；若未优于基线，保留基线。RSS、冷耗时、重复耗时和实际 `cache_n` 分别报告，不以理论内存量代替实测。

2026-09-25 09:40（UTC+8），在首轮Q8开发样本冷请求131.75秒、尚未进行测试集评估时，另行声明补充`prefix8`组。其假设是保留8K容量收益，同时绕开此次CPU上Q8 KV较慢的prefill路径。首轮六组不变，补充组在独立输出目录顺序运行相同三个开发样本和重复规则，仍按上述质量门槛及平均耗时参与最终开发集筛选。此为根据开发集结果扩展的配置搜索，不属于六组全部事先固定的比较；原始筛选协议副本和各轮协议均保留。测试集仍只运行基线及最终候选，不据测试结果换第二名。

候选选定后写入独立 selection.json，再运行 baseline 与候选的完整 12 条测试。只有同样质量门槛通过才建议启用；测试集不用于改参数、选第二名或补训。若测试退化，保留基线，明确报告优化未通过。即使相对质量不退化，少量合成且共享模板的样本也不能证明真实邮件质量达标。

## 实现边界

`schema-first-v1` 只重新排列用户消息 JSON 的键：完整 schema 位于动态候选、时间和新文本前，system 指令不变，数据不提升为指令。KV 缓存复用相同 token 前缀，不缓存图谱答案，不省略权限、证据、事务与幂等校验。不同请求即使逻辑相似，只有实际共同前缀可复用；单槽位并发排队和上下文变化可能减少收益。

8K 配置降低最大可容纳上下文，Q8 配置改变 KV 数值精度，Flash Attention 及缓存改变计算路径，均可能改变输出。禁止上下文滑动、自动 fit、截断和自动退回其他配置；超长输入或服务错误明确失败。启动器 `--profile` 与 API 的 `GRAPH_LLM_PROFILE` 必须相同。审计中的 `requested_inference_config` 表示请求配置，并不代替 `/props`、启动日志与服务命令对实际配置的核验。

## 复现

需要 Python、requests、jsonschema、psutil，以及原始冻结数据目录和官方 CPU llama-server。运行 `backend/tools/benchmark_graph_inference.py --help` 查看必需路径。首轮开发筛选使用 `--profiles baseline context8 flash8 kv8 prefix16 combined8 --split dev`；补充组另用新目录运行`--profiles prefix8 --split dev`；完整测试使用 `--profiles baseline prefix8 --split test`。每次 `--output` 必须为新目录；原始请求/响应仅含本轮合成样本，仍应按实验资料保管。

基准工具核验模型与语料文件哈希，保存协议、启动命令、原始响应、评分和两秒一次的进程树 RSS 采样。桌面负载未隔离；一次运行不能给出统计置信区间，进程树 RSS 可能重复计算共享页。报告推理 tokens 和 prefill/decode 时间，以区分算法加速与输出长度变化。服务器使用自身 2 线程复测，不能把本机 8 线程结果当服务器性能。

## 运行配置

模型启动器增加 `--profile <配置名>`，API进程设置 `GRAPH_LLM_PROFILE=<相同配置名>`。未配置时两端均为baseline，未知名称直接失败。只有修改API环境不能改变已运行模型的上下文/KV类型，必须同步重启模型。上线核验服务启动命令、`/props`的实际上下文与槽位数，以及模型响应`timings.cache_n`；`model_audit.inference_profile`、`requested_inference_config`和`timings`随来源保留。

仅用于复现本轮未通过启用门槛的候选实验，完整启动参数为：

```bash
python backend/tools/run_graph_model.py \
  --executable /absolute/path/llama-server \
  --model /absolute/path/Qwen3-4B-SalesMate-Semantic-v2-Q4_K_M.gguf \
  --variant semantic-v2 --threads 2 --port 8088 --profile prefix8
```

API进程环境设置`GRAPH_LLM_URL=http://127.0.0.1:8088/v1`、`GRAPH_LLM_MODEL=salesmate-graph`、`GRAPH_LLM_PROFILE=prefix8`。已有HTTP/MCP参数不变，模型服务仅绑定回环地址。两线程示例针对此次服务器，本机对照仍显式使用八线程。

回到基线时显式把两端改为baseline并重启。此操作是管理员选择，系统不会因超时自动执行。重启清空KV缓存，首条请求再次需要完整prefill；服务health就绪也不表示前缀已经预热。8K配置下既有80000字符业务边界并不保证token预算可容纳，大输入仍可能被模型拒绝，服务不截断或悄悄扩大上下文。

## 结果

开发集筛选完成，候选为`prefix8`。下表单位为秒，RSS为进程树采样峰值（GiB）：

| 配置 | 3条非重复均值 | 第一条冷请求 | 相同输入重复 | RSS |
|---|---:|---:|---:|---:|
| baseline | 89.09 | 91.45 | 97.88 | 6.38 |
| context8 | 62.38 | 66.30 | 67.36 | 5.26 |
| flash8 | 64.48 | 69.14 | 67.83 | 5.26 |
| kv8 | 129.71 | 131.75 | 131.38 | 4.73 |
| prefix16 | 31.64 | 64.49 | 19.58 | 6.38 |
| combined8 | 57.57 | 139.91 | 19.38 | 4.73 |
| prefix8 | 30.95 | 63.02 | 17.84 | 5.26 |

七组在这3条上的质量相同：2条通过契约校验、1条事实完全正确、TP=0/FP=1/FN=3。不能把这个开发筛选说成“建图准确”；首条漏掉关系目标实体，联系人场景存在错误关系，正确条目是无产品需求的否定场景。缓存组重复请求实际复用4138个tokens，后续不同输入复用4116个tokens。Q8 KV在此CPU上明显拖慢prefill；prefix8与prefix16的开发均值只差约2%，不构成统计意义上的速度优势，prefix8另有较低内存占用。

完整12条测试结果（不含重复请求的质量与均值）：

| 指标 | baseline | prefix8 |
|---|---:|---:|
| 模型HTTP请求平均秒数 | 62.47 | 18.31 |
| 第一条无KV缓存请求秒数 | 70.13 | 66.70 |
| 相同输入重复请求秒数 | 70.03 | 22.52 |
| 平均prefill秒数 | 46.05 | 4.70 |
| 平均decode秒数 | 16.40 | 13.60 |
| 平均生成tokens | 135.67 | 126.42 |
| RSS采样峰值GiB | 6.40 | 5.26 |
| 契约通过 | 8/12 | 7/12 |
| 事实完全正确 | 6/12 | 6/12 |
| TP / FP / FN | 4 / 2 / 8 | 4 / 0 / 8 |
| 事实micro-F1 | 0.444 | 0.500 |

平均加速约3.41倍，主要来自共同输入前缀的计算复用；部分输出长度也变短，不能把全部收益归因于计算内核。首条没有类似幅度的提速。联系人测试从“可校验但关系错误”变为缺失关系目标而拒绝；歧义名称测试减少了误报，但仍漏检。虽然FP减少且F1提高，契约通过数下降，按事先规则判定**未通过启用门槛**。没有据测试集换第二名或重新调参；没有放宽任何校验。

本机计时从发送模型HTTP请求到收到响应，包含随后被评分器判为失败的输出，不含图谱数据库写入。因此18.31秒不是“成功建图API”的平均延迟。

46项数据库/契约回归测试通过；补充prefix8后7项配置测试再次通过。270个后端、11个集成Python文件文档检查通过，注释差异检查0错误、0待复核；迁移检查无变更。第一次数据库测试遭遇WSL PostgreSQL停止，第二次受到中断遗留测试数据影响；保持WSL运行并完成测试库清理后，完整46项成功重跑，失败日志保留。

原始基准位于本机`output/semantic-optimization-20260925/`，公开汇总及逐例计时/评分见[验证记录](semantic-inference-verification.json)。

## 服务器临时验证

已先推送代码提交`a5c60d0f029b00d6d853fcfc42904bd5e54d9635`，再部署至既有隔离目录；502个Git源码文件逐一验证SHA256。权重由启动器再次校验，实测`/props`为8192上下文、1槽位，API日志明确为prefix8，CPU线程为2。候选测试未触及生产数据库或生产站点代码。

- 模型在摘要校验后约83.82秒完成初始化；这是加载时间，不计入以下请求延迟。
- 匿名工具访问401；48类schema、结构化输入及相同来源重放通过。
- 自然语言冷请求在**300.28秒返回HTTP 502 / ReadTimeout**。日志显示2048个输入tokens处理243.96秒（8.39 tokens/s），完整输入仍未完成。
- 超时来源查询覆盖沙盒全部4个来源，确认未写入该文本来源；未重试。客户端取消后显式停止模型进程，结束未完成计算。
- 模型cgroup快照约3.20 GB内存、2.89 GB交换占用；`vmstat`的有效间隔样本有约10–22 MiB/s换入、17%–31% I/O等待，显示内存与磁盘换页压力。该cgroup数据不是本机进程树RSS指标，不能直接作等口径比较。
- 真实stdio MCP连接真实HTTP后端，9项图谱工具发现、结构化写入、来源重放、查询及撤回闭环通过；**此MCP冒烟没有调用LLM**。

此轮没有完成服务器热请求或并发/长文性能测试，不能宣称服务器自然语言建图已可用。原站点ready健康检查在测试期间保持ok。候选既未通过本机启用门槛，也未解决服务器冷请求超时，因此实验结束后显式恢复baseline；不提高300秒阈值，不自动切换模型或修复答案。

隔离服务器以`app`符号链接指向`releases/<Git提交>`保留版本，`deployed-revision`记录实际源码提交。模型配置位于systemd的`inference-profile.conf` drop-in，API配置位于私有`runtime.env`；这两处必须同步设置。Gunicorn 26.2的私有控制目录需要由专用用户写入，本次已建立`/opt/salesmate-semantic/.gunicorn`（0700、salesmate-graph所有），修正初始化日志中的目录权限错误。
